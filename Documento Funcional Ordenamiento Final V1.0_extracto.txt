Descripción General del Proceso.
Dentro de la solución Reconocer Máster, Experian definió un modelo estadístico con el cual tomando la información reportada hacia el buró de las ubicaciones de las personas, pudiese identificar cual de todos los tipos (Direcciones Físicas, emails, Teléfonos Fijos, Celulares) era más probable contactar a la misma.
Para esto, y a través de un modelo estadístico, se puede computar, puntuar y luego ordenar la información de tal forma, que se establezca una numeración ascendente para cada dato, desde el más probable (1) hasta el menos probable (n). 
Este algoritmo se aplica por separado para cada uno de los tipos de ubicación (Dir, Email, Cel, Tel) y cada criterio es diferente y fue definido para calificar, a través de un mecanismo llamado características. (Ver Apéndice Conceptos)
Reglas Generales de Negocio:
Para realizar el ordenamiento de las ubicaciones se tienen en cuenta las siguientes reglas generales y que se encuentran contenidas en la lógica de negocio (Ver Apéndice A. Lógica de Negocio) requeridas por Experian:
No se Ordenan Ubicaciones que no sean válidas, resultado de algoritmo de estandarización (Ver Documentos Algoritmo Estandarización)
No se Ordenan Ubicaciones que hayan sido unificadas, resultado del algoritmo de unificación (Ver Documentos Algoritmo Normalización)
Solo se ordenan ubicaciones con cuentas activas para la fuente ICBDIR (Suscriptor) y para las otras fuentes no se asocian cuentas a las personas y sus ubicaciones (Contactabilidad, CIU, etc.)
Se generan 3 fechas de insumo por cada Persona – Cuenta – Suscriptor. Esto con el fin de cumplir con lo requerido por el algoritmo para el cálculo de número de meses de reporte. (Ver Apéndice E. Conceptos de Negocio)

Flujo de Datos de la Solución / Diseño Propuesto:
Para el cálculo del ordenamiento, se requiere tener disponible y actualizada la información contenida en el modelo de datos Reconocer Máster y BDM (Business Data Model) de Experian.
Reconocer Máster administra toda la información relacionada con los datos de ubicación de las personas: 
Ubicaciones Originales: Información de todas las ubicaciones por personas, reportada por los suscriptores del buró y tal cual llega escrita textualmente al negocio sin ninguna clase de procesamiento o mejora. (Ver documentos del modelo de datos Reconocer Máster)
Ej:
Ubicaciones Estandarizadas: Es la información procesada, mejorada y validada por parte de varios mecanismos, que permiten tomar las ubicaciones reportadas (Email, Tel, Cel, Dir) hacia el buró y dejarlas de una manera legible y “estándar” para su consumo o uso por parte del negocio o los clientes del buró. (Ver Documento Algoritmo Estandarización).
Ej:
Ubicaciones Unificadas (Solo Direcciones Físicas): Es la información de direcciones físicas, que, a través de un algoritmo, permite “unificar” desde la puerta todos los complementos o en su defecto las mismas direcciones independientes de su tipo de uso (Ver apéndice Conceptos y Documento Algoritmo de Unificación)
Ej:
BDM guarda toda la información del Buró y esto incluye las siguientes dimensiones:
Personas: Información de los datos personales de las personas, priorizadas por tipos y números de identificación de acuerdo con la fuente que reporte. 
Cuentas: Toda la información de las cuentas asociadas a los suscriptores del buró. Aquí se administra la información de Saldos en Mora, meses de mora, endeudamiento, Comportamientos Activo y pasivo, etc.
 A partir de estas fuentes de información, se realiza todo un proceso que se desprende de la siguiente manera:

En esta parte del proceso se genera una tabla con todas las personas que tuvieron cambios en ambos modelos de datos. No son excluyentes.

1.5 Alistar Insumo Características: Para el alistamiento de insumos de características, se realizan varias operaciones a nivel de bases de datos que son en sí, consultas tanto al modelo de datos de reconocer (Ubicaciones) y el buró (BDM) con el ánimo de obtener todas las variables necesarias para usarlas como insumo en los cálculos de características estándar y personalizadas, para luego aplicar el respectivo ordenamiento. El proceso por cada tipo de ubicación (Dir, Email, Tel, Cel) es el mismo, ya que la normalización del modelo físico tiene tablas que guardan toda la información independientemente de las fuentes (SUS, CIU, Contactabilidad) en Reconocer.

Diagrama 4. Detalle Subproceso Consultar Atributos Persona – Ubicación
Donde:
Se Identifican los lotes de los procesos que modificaron las tablas tanto en el Modelo de Reconocer como en BDM a partir de las tablas de Log (Log_TD y MetadataCargaLog) respectivamente. Esto recibe como input una fecha de ejecución o en su defecto la fecha de último ordenamiento que el proceso automáticamente administra (Ver Apéndices A. Lógica de Negocio y B. Tablas del proceso)
Identificadas las tablas del modelo que sufrieron cambios, se procede a partir de consultas, extraer los códigos de personas (Id Buro Persona y Cod Pin Persona) de todas aquellas que sufrieron cambios con los números de lotes del paso anterior, es decir cuales lotes y sus personas son los potenciales para ordenar. (Ver Apéndice B. Tablas del proceso)
Obtenida la base inicial de personas consolidada (Insumo Personas) se tiene el input para iniciar la búsqueda de variables y “armar las sábanas” con toda la información de Personas, Ubicaciones, Cuentas y Características estándar.
En este punto, está toda la lógica consolidada en procedimientos almacenados de los cruces de información que se realizan dentro del modelo BDM – Reconocer para obtener la base de Cuentas que se usa para calcular Características Estándar y Personalizadas.
Dentro de los pasos 5 y 6, se genera el alistamiento de la tabla final que guarda la información de todas las personas y sus cuentas. La salida genera la tabla REC_STAGE.CTA_TOTALES_PERSONAS_TMP3 que llamamos Insumo de Cuentas. (Ver Apéndice B. Tablas del Proceso)
Dentro del subproceso 1.2., se ejecuta en paralelo el cálculo de la información de direcciones, que al final entrega el Insumo de Ubicaciones que no es más que la tabla REC_STAGE.DIRECCIONES_TEMP. Complemento_Dir
Tabla que contiene un listado de todos los complementos asociados a las direcciones de los clientes. 
 
CREATE TABLE Complemento_dir AS  (SELECT c.tipo_id,          c.num_id,          c.direccion_ge,          c.complemento,          d.maximo_longitud+maximo+numero+longitud AS suma   FROM     (SELECT a.*,             b.maximo      FROM        (SELECT tipo_id,                num_id,                direccion_ge,                complemento,                CASE                    WHEN complemento<>'' THEN length(complemento)                    ELSE 0                END longitud,                CASE                    WHEN direccion_ge<>''                         AND complemento<>'' THEN count(*)                    ELSE 0                END numero         FROM copia_base_dir         GROUP BY tipo_id,                  num_id,                  direccion_ge,                  complemento) a      LEFT JOIN        (SELECT tipo_id,                num_id,                direccion_ge,                max(numero) maximo         FROM           (SELECT tipo_id,                   num_id,                   direccion_ge,                   CASE                       WHEN direccion_ge<>''                            AND complemento<>'' THEN count(*)                       ELSE 0                   END numero            FROM copia_base_dir            GROUP BY tipo_id,                     num_id,                     direccion_ge,                     complemento) a         GROUP BY tipo_id,                  num_id,                  direccion_ge) b ON (a.tipo_id=b.tipo_id                                      AND a.num_id=b.num_id                                      AND a.direccion_ge=b.direccion_ge)) c   LEFT JOIN     (SELECT tipo_id,             num_id,             direccion_ge,             max(length(complemento)) maximo_longitud      FROM copia_base_dir      GROUP BY tipo_id,               num_id,               direccion_ge) d ON (c.tipo_id=d.tipo_id                                   AND c.num_id=d.num_id                                   AND c.direccion_ge=d.direccion_ge));
